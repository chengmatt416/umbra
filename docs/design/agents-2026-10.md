## 0. What exists today and what we build on

| Need | Already there | Gap |
|---|---|---|
| Sessions | `AgentSupervisor` runs omp sessions in the guest; `Session` record; admission queue (ADR 0021) | no addressing between sessions, no "kind" |
| Subagents | omp's `task` tool spawns in-process subagents with an `effort` (lo/med/hi); `Session.subagents` brief | omp 18.8.2 removed per-call `model` from `task`, and its subagents cannot be messaged while they run |
| Effort | omp thinking levels (off…max) and an `auto` classifier (`auto-thinking/classifier.ts`) | no UI, Laya is not the judge |
| Browser | omp `browser` tool (Chromium, aria snapshots), `computer` tool, Linux desktop (ADR 0007) | no Chromium in the rootfs, no pack |
| Background screens | virtual displays + Capsule + accessibility control | no per-app ownership, no "user opened the same app" rule |
| Nodes | Kotlin `umbra-node` (JVM), mTLS pairing with a 12-char code, manifests, leases (ADR 0018) | no VNC, no installer, needs a JVM |
| Model choice | `AutoModel` asks Laya per task | — |

## 1. Two kinds of session **(decided)**

| | Coding session | Agent |
|---|---|---|
| Purpose | Get one piece of work done fast; many in parallel | A 24/7 assistant that knows the user |
| Lifetime | Ends when the task ends | Runs until the user stops it |
| Tools | Terminal, Linux desktop, headless browser, files, subagents | Messages, notifications, timers, memory, other agents, start coding sessions |
| UI | Today's task page (chat · steps · terminal · changes), unchanged | Telegram-style chat |
| Started from | FAB menu "New coding session" | FAB menu "New agent"; **the Capsule talks to the default agent** |

`Session` gets `kind: CODING | AGENT` and `agentId`. An agent is a `AgentProfile` record plus one long conversation;
the omp process behind it is started on wake and stopped when idle (§8), so "always on" does not mean "always
holding 300 MB".

### FAB menu
The expanded menu keeps its entries; under them, one row with two equal pills side by side:
**[+ Coding session] [+ Agent]** (left/right swap for left-handed mode). The single "+" FAB is unchanged.

### Home
Two segments at the top: **Agents** (Telegram chat list: avatar, name, last line, time, unread badge, a small
"next wake 14:20" line) and **Coding** (today's task list, unchanged). The segment remembers the last choice.

## 2. Agent profile: soul and memory

Each agent lives in `agents/<id>/` (app private, backed up with the vault key):

* `SOUL.md` — who it is: name, tone, what it is for, rules ("never reply to my boss without asking"). Written by the
  user in a guided form (name, avatar, role template, free text) and editable as text.
* `MEMORY.md` — what it learned about the user. The agent appends through a `memory` tool; each entry has a date and
  source ("from WhatsApp, 12 Oct"). The user can read, edit and delete entries. Coding-session reports add here too.
* `profile.json` — model, effort, channels it watches (connector + chat filters), notification apps it reads,
  autonomy per contact, heartbeat interval, quiet hours, Telegram bot link.

Multiple agents: each has its own soul, memory and channels. Templates offered: Personal assistant, Inbox triage,
Work, Blank.

## 3. Session-to-session messages (like Claude Code's `SendMessage` / `ListAgents`)

Host tools given to every session (coding and agent):

| Tool | Does |
|---|---|
| `sessions_list` | Live and recent sessions/agents with name, kind, state, one-line status |
| `session_send(to, message, expect_reply?)` | Delivers a message into the target's conversation, tagged with the sender |
| `session_reply(message_id, text)` | Answers a message; the answer arrives in the sender's conversation as a message |
| `session_read(to, since?)` | Reads the target's recent progress (steps, last turn) without disturbing it |

Delivery: if the target is idle it is woken with the message as a new turn; if it is running, the message is queued
and given at its next turn boundary (omp `steer` only when `urgent`). Names are short handles (`#refactor-auth`,
`@Mia`). Guards: a hop counter (a chain stops after 6 hops), 20 messages/min per pair, no message to a stopped
session (error back to the sender). Every message appears in both conversations as a small "from #x" bubble, so the
user can see the traffic.

## 4. Subagents

Umbra subagents are **child sessions**, not omp's in-process `task` (which cannot be messaged mid-run):

| Tool | Parameters |
|---|---|
| `subagent_start` | `task`, `model` (id or `auto`), `effort` (`low…max` or `auto`), `name`, `wait` (bool) |
| `subagent_status` | `name` → state, current step, last 20 lines of activity, tokens |
| `subagent_send` | `name`, `message` (same delivery rule as §3) |
| `subagent_wait` | `names`, `timeout` → final reports |
| `subagent_stop` | `name` |

* Same working directory (the parent's workspace), same permission profile and approval rules as the parent. **(decided)**
* `parentSessionId` links them; the parent's task page shows a **Subagents** strip (name · model · effort · state ·
  current step); tap opens the child's chat; the user can message or stop it too.
* Children count against the governor like any session; when the phone cannot run another, `subagent_start`
  returns "queued" and the parent may wait or continue.
* omp's own `task` tool stays disabled for Umbra sessions so there is one mechanism (since omp 18.8.2 it cannot take a
  model per call anyway).

## 5. Effort for normal sessions **(decided: user choice or Auto)**

Composer gets a second chip next to the model chip: **Effort · Auto** (Simple and Power composers alike). Sheet: Auto, Low, Medium, High, Extra high,
Max (only levels the chosen model supports; others greyed with "not on this model"). Auto: Laya classifies the
request (trivial / moderate / hard → low / high / xhigh, same mapping as omp's classifier); without Laya, omp's own
`auto` judge; failure falls back to Medium. The chosen level shows on the task header ("Auto → High"). It can be
changed mid-session (omp `set_thinking_level`). Agents have an effort in their profile (default Auto).

## 6. Message app connectors

### 6.1 Methods

| Method | How | Reads | Sends | Risk |
|---|---|---|---|---|
| **N · Notification bridge** | `NotificationListenerService`; reply through the notification's `RemoteInput` action | new messages only | reply to a chat that notified | none |
| **V · Visual** | the real app on a background virtual display, driven by accessibility + vision | full history | anything the app can | low; slow; conflicts (6.3) |
| **A · Official API** | user's own key/token/server | full | full | none |
| **U · Unofficial client** (opt-in) **(decided)** | reverse-engineered protocol library in the guest | full | full | **account ban** — amber warning, off by default, per-app consent |
| **S · System** | Android providers / SmsManager | full | full | none |

### 6.2 Per app

| App | Methods offered (default first) | Notes |
|---|---|---|
| Phone messages (SMS) | S, N | `READ_SMS`/`SEND_SMS` (sideload, targetSdk 28). RCS has no API → N or V on Google Messages |
| Telegram | A (TDLib user login: phone + code, user's own `api_id`), N, V | official and allowed |
| WhatsApp | N, V, U (Baileys, linked device by QR) | Business Cloud API not offered (cannot use a personal number) |
| Instagram | N, V, U (instagrapi) | Graph API messaging is for professional accounts only; offered as A for those |
| Messenger | N, V, U | Graph API is for Pages only; offered as A for Pages |
| LINE | N, V | LINE Messaging API is for official accounts (bots) only; no safe unofficial client → not offered |
| OpenBubbles (iMessage) | A (BlueBubbles server REST + socket: URL + password), N, V | needs the user's Mac server |
| Snapchat | N, V | no API; Snapchat detects automation → V shows an amber note |
| X | A (X API v2 DMs, user's OAuth/keys; paid tier), N, V, U | |

Every connector exposes the same internal interface (`chats`, `messages(chat, since)`, `send(chat, text, media)`,
`events`), so agents never care which method is underneath. A connector can have several methods enabled; reads use
the richest available, sends follow the user's order. Messages are stored locally (`messages.db`, SQLCipher with the
vault key), retention user-set (default 30 days).

### 6.3 Conflict prevention (Visual method)
* **App lease**: one owner per app package at a time (a visual worker, or the user). Workers queue for the lease.
* **User comes first**: an accessibility window-change watcher on the main display. When the user brings the same
  app to the foreground: the worker stops at the next safe point (never mid-typing: it clears what it typed),
  releases the task back, and the Capsule shows "Paused WhatsApp — you're using it". When the user leaves the app
  and 5 s pass with it in the background, the worker re-launches it on its virtual display and resumes.
* Never two Umbra workers in one app; no visual work in an app while a call is active, or during the user's quiet
  hours if the profile says so.
* Sends through V show in the Capsule as they happen and can be stopped with one tap.

### 6.4 Sending policy **(decided)**
Default: the agent drafts and **asks** (Capsule card + Telegram-bot inline buttons: Send / Edit / Don't). Per chat
the user can set "may reply on its own". Groups never default to auto. Every sent message is logged with the
method and the agent.

## 7. Notification reader
* `NotificationListenerService` (user grants "Notification access"; Onboarding step for Agent users).
* Per-app list: Read & use / Read only for context / Ignore. Defaults: messaging apps = use; banking/OTP/2FA apps
  and anything with a one-time code = **ignore** (code-like content is redacted before storage even when allowed).
* Stored in `notifications.db` (encrypted), default 7 days, with app, title, text, time, actions. Duplicates of
  connector messages are merged.
* Feeds the agents' event bus (§8) and a `notifications_query` tool. Settings → Notifications shows the log and a
  "forget all" button.

## 8. Always-on agents and power **(decided: 10 min default)**

The agent scheduler lives in the existing foreground `AgentService` (already survives reboot via `BootReceiver`).
It holds no LLM process while idle.

Wake reasons, cheapest first:

1. **Heartbeat** every 10 min (Power/Dev: user-set, 5 min–6 h). `AlarmManager.setExactAndAllowWhileIdle` — in Doze
   Android allows about one such alarm per 9 min per app, which fits 10 min. On wake: build a digest (new messages,
   notifications, due timers, queue items, coding reports since last wake). **Empty digest → sleep again, no model
   call.** Non-empty → step 2.
2. **Triage gate** (on-device): Laya if downloaded, else rules (muted chats, sender importance from MEMORY.md) and
   then the cheapest connected model with a one-question prompt ("needs action now / later / no"). "No" items are
   noted for the next real run.
3. **Agent run**: omp process starts (or resumes the session file), gets the digest as a turn, acts, then is stopped
   after 2 min idle.

Immediate wakes (skip the heartbeat wait): a timer/cron the agent set fires; an item in the **proactive queue**
(user-defined "when X then Y" rules and the user's own queued requests) triggers; a message arrives from a
connector or the Telegram bot → triage gate only (step 2), run only if needed.

Agent tools: `timer_set(at|cron, note)`, `timer_list`, `timer_cancel`, `queue_add/list`, `memory_add/edit`,
`notify_user(text, priority)`, `messages_*`, `notifications_query`, `coding_start(task, model, effort)`,
`sessions_*` (§3).

Battery budget shown in Settings → Agents: wakes today, model runs today, estimated battery %. Battery saver or
temperature ≥ 42 °C doubles the heartbeat; below 15 % battery only immediate wakes run.

Consistency: an agent stays on until the user stops it (chat menu → Stop agent). Stopped agents keep soul, memory and
history and can be restarted.

## 9. Coding session → agent
A coding session started by an agent (`coding_start`) or assigned to one reports back: when it ends (or asks for
approval), a **report card** appears in the agent's chat (title, result, files changed, time, cost, "open"). The agent
gets the report as an event; it may add to MEMORY.md ("prefers Kotlin, tests before commit"). Coding sessions the user
starts can be assigned to an agent from the task menu.

## 10. Headless browser for coding sessions
New guest pack `browser`: Debian `chromium` (arm64) + fonts, picked up by omp's `browser` tool.
* **DOM way** (Playwright-style): omp `browser` — navigate, aria snapshot, click by role/name, fill, evaluate,
  screenshot; headless, no display.
* **Visual way**: headful Chromium on the Linux desktop (X11), driven by screenshots + pointer/keyboard (omp
  `computer` tool against the X display). The live display card shows it.
The session's settings pick DOM / Visual / Auto (Auto = DOM, fall back to visual when a page blocks automation).

## 11. Reaching an agent by a Telegram bot
* Settings → Agents → *agent* → Telegram bot: steps (1) open @BotFather, `/newbot`, copy the token; (2) paste;
  (3) Umbra shows a one-time link `t.me/<bot>?start=<code>`; opening it binds the bot to **that Telegram user id
  only**; other users get no answer.
* Umbra long-polls `getUpdates` from the phone (no server). Needs the battery-optimisation exemption so network
  stays up in Doze; without it, replies may wait for the next heartbeat (said on the screen).
* Bot features: text and voice (transcribed), photos/files in and out, approvals as inline buttons, `/agents` to
  switch agent, `/status`, `/stop`.

## 12. Remote node with VNC **(decided: Go rewrite; LAN + Tailscale/VPN)**
* `umbra-node` is rewritten in Go (single static binary, darwin/linux × arm64/amd64), keeping the ADR 0018 protocol
  (pairing proof, pinned mTLS 1.3, manifests, leases, revocation) so the phone side is unchanged.
* VNC: the node enables or starts a local VNC server and **tunnels it inside the mTLS link**; port 5900 is never
  opened to the network. macOS: built-in Screen Sharing (wizard guides the switch) or the node's own ScreenCaptureKit
  RFB server (needs Screen Recording + Accessibility permission). Linux: `x11vnc` on X11, `wayvnc` on wlroots,
  GNOME Remote Desktop (`grdctl`) on GNOME Wayland.
* Phone: an RFB client in the app. The user sees the node in Displays (view, take over); agents get a `remote_screen`
  target: screenshot from the framebuffer, pointer/keys as RFB events, same vision pipeline as phone screens.
* Reachability: LAN address; outside the LAN the wizard detects Tailscale (or any VPN interface) and offers its
  address; pairing QR carries every address.

## 13. Node setup wizard (GUI + TUI, macOS + Linux)
Install:
* `curl -fsSL https://umbra-agent.pages.dev/node | sh` (`/node` serves `install.sh`; `/node/install.sh` for people who
  read before running) — detects OS/arch, downloads the binary, checks its
  SHA-256 and minisign signature, puts it in `~/.local/bin`, then runs `umbra-node setup` (TUI when on a terminal).
* Website "Remote node" section: macOS `.dmg` (universal), Linux `.AppImage` and `.tar.gz`, plus the curl line with a
  copy button. Double-clicking opens the GUI wizard.

Same steps in both interfaces:
1. **Check** — OS, arch, network addresses, VNC backend available, free disk.
2. **Pair** — QR code + 12-character code; phone scans in Nodes → Add node. Shows the phone's name to confirm.
3. **Screen access** — enable VNC: per-OS instructions and live status (macOS permission panes opened for the user;
   Linux backend choice). Skippable (node then runs jobs only).
4. **Reach** — LAN address, Tailscale/VPN detection, test from the phone.
5. **Run in background** — launchd agent (macOS) / systemd user unit (Linux), start at login.
6. **Done** — status, `umbra-node status` hint, uninstall command.

GUI: Wails (Go + system webview), Porcelain styling. TUI: Bubble Tea, keyboard-only, same copy.
`umbra-node setup --gui|--tui`, `umbra-node status`, `umbra-node uninstall`.

## 15. Decided after review (2026-10-18)
1. **macOS .dmg is ad-hoc signed** (`codesign --sign -`), not notarized. The download page and the .dmg's background
   say how to open it the first time (right-click → Open, or System Settings → Privacy & Security → Open Anyway; on
   macOS 15+ the latter). The curl install is unaffected (no quarantine flag).
2. **Telegram user login (TDLib) uses the user's own `api_id`/`api_hash`** from my.telegram.org, entered under an
   *Advanced* section of the Telegram connector. Without them Telegram uses the notification bridge and visual methods.
3. **Agent avatars are generated**: Umbra ships a set of generated avatars (several styles, in the Porcelain palette);
   the new-agent sheet shows them in a grid to choose from, with a letter avatar as the fallback.
