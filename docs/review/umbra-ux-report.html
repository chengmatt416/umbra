摘要

功能範圍很完整，架構設計也很嚴謹，但 使用者介面還沒有跟上功能。最需要先處理的是三件事：會直接刪除資料的操作沒有確認（工作區、任務、核准歷史），同一個「停止」或「核准」在不同入口的行為不一致，以及 首次設定與進階選項一次全部攤開。另外，計畫頁的按鈕文字會被截斷，Snapshot 工具列與分段控制的對齊也需要修正。

嚴重程度：高＝可能造成資料遺失、安全誤判或基本流程失敗中＝會讓人做錯或停下來低＝外觀或文字

建議的修正順序（前 10 項）

  1. C-01　Workspace 的 Delete：移除 force，加確認
  2. C-02　任務的 Delete 加確認
  3. C-03　核准歷史的 Clear 加確認，或保留紀錄
  4. L-01　計畫頁的按鈕文字不要在字中間截斷
  5. S-01　無障礙受限設定：拆成步驟並在偵測到時顯示
  6. C-07 / C-08　核准規則統一；通知列不提供 HIGH／CRITICAL 的一鍵核准
  7. X-01　首次設定分成必要與進階
  8. C-04　Stop all 與通知 Stop 統一行為，並加確認
  9. C-09　Take Back Screen 改名並說明範圍
  10. F-03　建立中文字串資源

1. 功能不夠完善

有些功能只完成一部分，或與規格不一致；介面沒有誠實說明這些缺口。

F-01高

緊急控制沒有「強制停止」，只有鎖定、暫停與停止

位置

  • docs/traceability.md（AC-007 部分；AC-008、AC-009 未建）
  • ui/emergency/EmergencyScreen.kt

使用者會看到

緊急控制提供 Lock down、Pause all、Take Back Screen。規格要求的分階段 Execution Halt（fence → checkpoint → stop → reconcile）沒有實作。

影響

鎖定能擋住新輸入，但無法保證停掉已在執行的程式。畫面上「What a lockdown does not guarantee」寫得清楚，但功能本身是不完整的。

建議

在 Emergency 頁為「停止」列出可以與不能保證的事；若要宣稱可安全停止，先完成 halt controller（AC-008、AC-009）。

F-02中

節點失聯時不會自動換節點接手

位置

  • docs/adr/0018-distributed-nodes.md §8
  • ui/nodes/NodesScreen.kt

使用者會看到

節點失聯的工作留給租約自然結束，要使用者自己再派一次。

影響

長工作在節點斷線時沒有人接手，使用者也未必知道要手動處理。

建議

在工作卡片上直接標示「需要手動重新派工」，並提供需授權的一鍵重派。

F-03高

介面只有英文，沒有字串資源

位置

  • app/src/main/res（沒有 strings.xml）
  • ui/ 與 capsule/ 約 1,250 條文字直接寫在 Kotlin

使用者會看到

規格與行銷素材是中文，App 內所有按鈕與說明都是英文。

影響

中文使用者的理解成本高；許多說明超過 100 字，英文閱讀負擔更重。

建議

抽出 strings.xml，先建立 values-zh-rTW，從 Setup、Approvals、Session 三個入口開始。

F-04中

部分功能只在模擬器或尚未在實機驗證，畫面上看不出來

位置

  • docs/traceability.md 第 8（Shizuku）、19（真實模型）、21（真實子代理）列
  • ui/SettingsScreen.kt（Laya 區塊）

使用者會看到

文件誠實標示未驗證；App 內 Shizuku、Laya 的入口與已驗證的功能外觀相同。

影響

使用者可能在未驗證的路徑上卡住，又不知道問題不在自己。

建議

對未在實機驗證的路徑加上標記，或把它們收進「進階」並說明狀態。

F-05低

原型中的 Design System 與「完整規格」在 App 中沒有入口

位置

  • 原型 Porcelain HTML 的導覽表（15 個表面）
  • ui/shell/PorcelainApp.kt（Dest 列舉）

使用者會看到

App 有 23 個目的地，但沒有 Design System 與 Complete Specification 頁面。

影響

若原型是產品規格的來源，使用者在 App 裡找不到完整規格。

建議

確認這兩頁是否屬於產品。若屬於，加入唯讀的 Reference 頁。

2. 需要修正（含資料與安全）

多個會刪除資料、清空紀錄或改變權限的操作，沒有確認，或在不同入口的規則不一致。

C-01高

工作區的 Delete 沒有確認，而且強制刪除

位置

  • ui/WorkspacesScreen.kt:96（delete(ws.id, force = true)）
  • core/workspace/WorkspaceManager.kt:99（未 force 時會擋住使用中的工作區）

使用者會看到

工作區下拉選單的 Delete 一點就刪除整個資料夾。

影響

任務產出的檔案不可復原。force = true 會略過「仍有任務在使用」的保護，正在執行的任務可能失去工作目錄。

建議

移除 UI 的 force；加確認對話框，列出仍連結的任務；或改為先移到垃圾桶。

C-02高

任務的 Delete 立即刪除，沒有確認

位置

  • ui/current/CurrentScreen.kt:248（supervisor.delete）

使用者會看到

Session 選單中的 Delete 直接刪除時間軸與私有檔案（工作區保留）。

影響

刪除不可復原，也沒有任何提醒。

建議

加確認，並寫明「保留工作區、刪除對話紀錄」。

C-03高

核准歷史的 Clear 一鍵清空紀錄，與 README 的承諾相反

位置

  • ui/ApprovalHistoryScreen.kt:53（container.ledger.clear()）
  • README.md：「Everything it asked and you answered is kept in a history.」

使用者會看到

頂列的 Clear 直接清空所有核准紀錄，沒有確認。

影響

審計紀錄可被一鍵清空，與產品「保留所有核准紀錄」的說法不一致。

建議

加確認；或改為只隱藏顯示、保留紀錄檔（append-only）。

C-04中

「Stop all tasks」沒有確認，而且和通知上的 Stop 行為不同

位置

  • ui/SettingsScreen.kt:168（supervisor.stopAll()，會清空佇列）
  • app/AgentService.kt:244（通知的 Stop 只停執行中任務，不清佇列）

使用者會看到

兩處都叫「停止」，結果不同。

影響

排隊中的任務會消失，但使用者以為只是停止執行中的工作。

建議

統一行為；按鈕旁寫明「包含排隊中的任務」，並加確認。

C-05中

移除 Linux 環境沒有確認

位置

  • ui/SetupScreen.kt:179（guest.uninstall()）

使用者會看到

單一按鈕就卸載約 2 GB 的 Linux 環境，標籤寫「Remove (keeps your workspaces)」。

影響

之後所有任務都無法執行，直到重新安裝。

建議

加確認，顯示大小與重裝方式。

C-06中

「Revoke helpers」沒有確認，會關閉背景顯示器與 shell 工具

位置

  • ui/SettingsScreen.kt:174

使用者會看到

直接忘記 helper。按下前沒有說明會關閉什麼；說明只在按下後的訊息中出現。

影響

背景工作會悄悄停止。

建議

加確認，列出會受影響的功能。

C-07中

CRITICAL 風險的核准，三個入口規則不一致

位置

  • ui/inbox/AttentionCards.kt:73（收件匣：Approve once 不分等級）
  • capsule/CapsuleUi.kt:205（膠囊：CRITICAL 不顯示）
  • app/AgentService.kt:176（通知：CRITICAL 不顯示）

使用者會看到

收件匣可以一鍵核准 CRITICAL；膠囊與通知只能按「Review in Inbox」。

影響

最危險的動作在最完整的介面反而最容易點到。

建議

收件匣的 CRITICAL 核准加第二步確認，並說明影響；或三處採用同一規則。

C-08中

通知列可以一鍵核准 HIGH 風險的動作

位置

  • app/AgentService.kt:176（HIGH 仍有 Approve）

使用者會看到

通知標題是「Approval needed — high risk」，同時提供 Approve，不需解鎖或確認。

影響

在通知列上誤觸即可核准高風險動作。

建議

HIGH 不提供通知核准，改為開啟收件匣。

C-09中

「Take Back Screen」只收回手機主螢幕，名稱讓人誤以為是全部螢幕

位置

  • ui/emergency/EmergencyScreen.kt:119
  • capsule/CapsuleUi.kt:257（Take Back）
  • app/AppContainer.kt:143（資源為 display:${displayId}，這裡只收回 display:0）

使用者會看到

按鈕名稱像是「收回所有螢幕」，但背景顯示器上的代理仍會繼續操作。

影響

使用者以為自己拿回了控制權，實際上不是。

建議

按鈕改為「Take back phone screen」，並在按下後顯示背景顯示器仍在運作；或擴大收回範圍。

C-10低

審批模式是全域設定，但 Session 也記錄了一份模式，而且從未被讀取

位置

  • app/AppContainer.kt:227（政策每次檢查都讀全域設定）
  • core/orchestrator/AgentSupervisor.kt:119（寫入 Session.approvalMode）

使用者會看到

設定頁的「When to ask you」沒有說明它會立刻套用到執行中的任務。

影響

使用者可能以為模式是每個任務各自設定的。

建議

設定頁加一句「立即套用到所有任務」；移除未使用的 Session 欄位，或真的做成每任務設定。

3. 對一般使用者太複雜

功能完整，但把架構語言與所有進階選項同時攤在使用者面前。

X-01高

首次設定一次列出 11 項檢查，還有三條提權路徑

位置

  • ui/CapabilityProbe.kt（11 列，其中 3 列是必要的）
  • ui/SetupScreen.kt

使用者會看到

無障礙、root、Privileged helper、Shizuku、背景顯示器、Linux、模型、通知、通知存取、電池、懸浮控制；說明中同時出現 proot、chroot、adb、Shizuku。

影響

一般使用者不知道該選哪一條。真正必要的只有 3 項，卻一次呈現 11 項。

建議

首屏只顯示 3 個必要項目；其餘收進「進階」。有 root 就用 chroot，沒有就自動用 proot，不讓使用者選。

X-02中

任務內的進階面板選項過多

位置

  • ui/current/OmpSheets.kt（438 行，約 20 項會改變代理狀態的操作）

使用者會看到

模型與思考強度、快速模式、三種訊息送達方式、自動壓縮與重試、快取保溫、分支、目標與 token 預算、子代理、統計⋯⋯

影響

日常只需要「追問、暫停、停止」，卻要在同一層看到全部。

建議

分成「基本」（追問、暫停、停止）與「進階」兩層。

X-03中

畫面直接使用架構規格的術語

位置

  • ui/services/SharedServicesScreen.kt（Alive ≠ transport ≠ ready ≠ functional、Circuit breaker、Single recovery owner）
  • ui/integration/CommitScreen.kt（Conditional write (lease on the old value)、Prepare · fence）
  • ui/planning/PlanningScreen.kt（Delegation tree ≠ phase order ≠ which processes belong to whom）

使用者會看到

這些句子是設計規格的語言，很多直接出現在主畫面。

影響

理解門檻高；多數使用者沒有 git 或分散式系統的背景。

建議

面向使用者的標題用白話；技術名詞收在「詳情」中。

X-04中

提交流程有五步、夾雜 Git 術語

位置

  • ui/integration/CommitScreen.kt（Propose → Validate → Authorize & publish → Read the remote → Verify · finalize）

使用者會看到

出現「Fast-forward」「Rewrites history」「Non-fast-forward permission」「Candidate, remote ref, fast-forward, evidence」等字樣。

影響

使用者要懂 fast-forward 才能判斷要不要授權。

建議

用兩句話取代：「可以直接發布」或「會改寫遠端歷史，需要你另外確認」。

X-05中

「停止」類的控制有 6 個以上入口，語意不同

位置

  • 頂列盾牌（Emergency Control）
  • Settings → Stop all tasks
  • 通知列 Stop（AgentService.kt:244）
  • Capsule 的 Stop
  • Current 的 Stop 選單（Stop this turn、Stop the task、Stop retrying）
  • Emergency 的 Pause all、Lock down、Take Back Screen

使用者會看到

Pause、Stop、Stop this turn、Stop all、Pause all、Lock down、Take back，各自的範圍與保留方式不同。

影響

使用者無法判斷哪一個會保留任務、哪一個會清空佇列。

建議

統一成三個動詞：暫停（可回來）、停止（結束任務）、鎖定（擋住代理）；每個入口標示範圍。

X-06低

核准有 4 種回答，記住範圍又有 3 種

位置

  • ui/inbox/AttentionCards.kt（Approve once、More → This app / This command / This category、Deny）

使用者會看到

This app、This command、This category 都在「本工作階段」內生效，文字相近。

影響

使用者很難分辨差異，容易選到範圍太寬的規則。

建議

預設只給「只這次」與「本任務內同類動作」兩個選項。

X-07低

終端機接管有三個相近的動詞

位置

  • ui/terminal/TerminalsScreen.kt（Take control、Ask to hand over、Return to agent）

使用者會看到

三個按鈕並排；「立即接管」與「請求交接」的差異沒有說明。

影響

使用者不知道按哪一個會立刻生效。

建議

合併成「接管」與「請求交接」兩個，歸還放在接管狀態裡。

4. 會卡住的地方

使用者會在這些地方停下來，而且畫面不一定告訴他為什麼。

S-01高

無障礙服務的開關是灰的，說明只有一句話

位置

  • ui/CapabilityProbe.kt:54

使用者會看到

文字是「If its switch is greyed out: Umbra's App info, ⋮ menu, Allow restricted settings.」，按鈕只寫「Open settings」。

影響

這是 Android 上最常見的阻擋點，使用者要自己去找 App info 與 ⋮ 選單。

建議

把步驟拆成三個圖示步驟；偵測到受限設定時自動顯示這些步驟。

S-02中

列出模型需要 Linux 已安裝，但依賴關係藏在提示裡

位置

  • ui/ModelsScreen.kt:133

使用者會看到

按「List available models」後才出現「No models found. The Linux environment must be installed…」。

影響

使用者會以為是金鑰或網路的問題，卡在模型設定。

建議

在按鈕旁直接寫「需要先安裝 Linux 環境（約 2 GB）」，並連到安裝頁。

S-03中

沒有 root 時，Git 發布完全不能用，畫面只說「加入 brokered credential」

位置

  • docs/adr/0022-git-credential-broker.md §6
  • ui/vault/CredentialVaultScreen.kt:127（Needs root）
  • ui/integration/CommitScreen.kt

使用者會看到

無 root 的手機（proot）無法使用 broker；發布按鈕失敗，只有一行提示。

影響

沒有 root 的使用者無法安全地發布，也不知道原因。

建議

在 Commit 頁頂部說明「此手機使用 proot，無法使用 broker」，並把可用的替代方式列出。

S-04中

核准 5 分鐘沒回覆就自動拒絕，畫面沒有倒數

位置

  • core/safety/SafetyGate.kt:23（approvalTimeoutMs = 5 分鐘）
  • 收件匣、膠囊、Current 都沒有剩餘時間的顯示

使用者會看到

任務顯示等待中；超時後代理收到「No answer」，工作被跳過。

影響

使用者回來時，工作已經失敗或被跳過，而且不知道是什麼時候發生的。

建議

顯示剩餘時間；剩 1 分鐘時發出通知。

S-05中

診斷「Run all」會接管手機，而且執行中不能取消

位置

  • ui/DiagnosticsScreen.kt:68

使用者會看到

說明寫著「It opens Settings and presses Home, so don't use the phone while it runs.」；畫面上沒有 Stop 按鈕，只有 Back。

影響

使用者無法中止，只能等它跑完或強制關閉 App。

建議

加入取消按鈕與進度；或改成不接管手機的測試。

S-06中

節點配對需要在自己的電腦上裝 Java 21 並執行指令

位置

  • README.md（Your computers as nodes）
  • ui/nodes/NodesScreen.kt（umbra-node serve --pair）

使用者會看到

配對要切換到終端機、輸入指令，再把十二碼的代碼輸入手機。

影響

一般使用者無法完成。這個功能本身合理，但入口沒有分級。

建議

標示為「給開發者」，並移到進階區。

S-07低

按鈕停用時沒有說明原因

位置

  • ui/integration/RepositoryHubScreen.kt:92（Clone… 需要 Linux 就緒）
  • ui/integration/RepositoryHubScreen.kt:121（Link… 需要專案）

使用者會看到

按鈕灰掉，旁邊沒有文字；Clone 的原因只在下方另一區塊出現，而且只在沒有未登錄項目時出現。

影響

使用者不知道要先做什麼才能啟用。

建議

在停用按鈕旁加一行原因。

S-08低

解除鎖定後，任務不會自動恢復，要逐一手動恢復

位置

  • ui/emergency/EmergencyScreen.kt（Nothing resumes by itself）

使用者會看到

解除後任務仍是 PAUSED。這是刻意的設計。

影響

使用者可能以為「解除鎖定」就等於「繼續工作」。

建議

解除前列出將保持暫停的任務；另外提供一個明確的「全部恢復」按鈕。

5. 資訊太密集

同一畫面塞進太多技術欄位，關鍵狀態被淹沒。

D-01中

金庫頁直接顯示原始日誌 JSON

位置

  • ui/vault/GitCredentialsCard.kt:108（Chain intact · N）
  • ui/vault/CredentialVaultScreen.kt

使用者會看到

截圖中是 `{"id":"git-e61ba3e37922","operation":"read",…}` 這樣的原始紀錄，上方是「Chain intact · 18」。

影響

一般使用者看不懂，也增加視覺噪音。

建議

預設只顯示最近三筆（讀取或發布、時間、結果）；原始 JSON 收在「查看紀錄」裡。

D-02中

節點工作列表每筆有 4–5 行技術欄位

位置

  • ui/nodes/NodesScreen.kt（335 行，抽出約 82 條文字）

使用者會看到

例如 `sleep 900 · chengmatt@MacBook-Air-M1-2.local · job-mv38fjer-9689 · policy rev. 5 · no files sent · Lease until 10:58 AM…`

影響

做得好的地方

以下是改版時不應該丟掉的設計。

  • 緊急鎖定寫清楚「不保證什麼」：不取消已送出的指令，也不停止已在執行的程式（EmergencyScreen）。
  • 最有破壞性的幾個動作有確認：Delete all history、Lift lockdown、撤銷節點、刪除 vault 項目（SettingsScreen、EmergencyScreen、NodesScreen、CredentialVaultScreen）。
  • 狀態用詞誠實：Not confirmed stopped、Outcome unknown、Revocation pending、Chain intact；不假裝已完成。
  • 首頁只顯示真實狀態，不顯示假的進度（HomeScreen 的註解也是這樣寫的）。
  • 核准可以在收件匣、膠囊、通知、Current 四處回答，而且 CRITICAL 的限制有考慮。
  • Capsule 的截圖選取明確寫著「snapshot, not live」，並預設關閉 Live context。

方法與限制

  • 讀取範圍：app/src/main 的 UI 與 capsule 共 45 個檔案（抽出 1,251 條文字字串，含少量程式碼雜訊，只用來比較畫面之間的相對密度）；核心模組的狀態機、審批、準入、提交閘道、節點、憑證、恢復；docs/adr、docs/traceability.md、架構規格 v0.1（嵌入原型 HTML）。
